# Parakeet Unified Android runtime options

Investigated 2026-09-30 against transcribe.cpp commit `4807edaf210d0d7e8a6f7fb2a44b65966a2797f0`. This is a source audit, with no Android build or phone benchmark. It answers whether using Handy's runtime is a credible alternative to tuning Outspoke's current ONNX implementation.

## What using Handy's runtime would buy

transcribe.cpp supports Unified through its public C streaming API. Its implementation carries the RNN-T decoder state, recomputes a bounded left/chunk/right encoder window, and folds retained right context and the remaining tail into one final emit. The final window adds silence for trained lookahead. This is a concrete implementation reference for reducing Outspoke's repeated final encoder calls. It does not remove encoder recomputation or guarantee immediate completion when capture has outrun decoding. [Unified documentation](https://github.com/handy-computer/transcribe.cpp/blob/4807edaf210d0d7e8a6f7fb2a44b65966a2797f0/docs/models/parakeet-unified-en-0.6b.md#streaming), [feed and finalize implementation](https://github.com/handy-computer/transcribe.cpp/blob/4807edaf210d0d7e8a6f7fb2a44b65966a2797f0/src/arch/parakeet/model.cpp#L2980).

The same GGUF weights support runtime selection of the six published context tuples, including 560 ms center/right and 1040 ms center/right. The default is 1040 ms each. A longer center reduces encoder calls per second but increases the time before a preview update. Smaller center/right values trade accuracy and overhead against lookahead; selecting the smallest tuple does not establish the fastest phone implementation. These settings are runtime choices in transcribe.cpp; Outspoke's present ONNX export supplies its window geometry through model metadata. [Public context extension](https://github.com/handy-computer/transcribe.cpp/blob/4807edaf210d0d7e8a6f7fb2a44b65966a2797f0/include/transcribe/parakeet.h#L70), [current ONNX engine](../app/src/main/kotlin/outspoke/inference/ParakeetUnifiedEngine.kt).

GGUF Q8_0 is 731 MB, Q5_K_M 541 MB, and Q4_K_M 477 MB. Upstream reports similar offline LibriSpeech accuracy for these variants, but its desktop tables do not show Q4 consistently outperforming Q8. Smaller files are a storage option, not evidence of faster Android decoding. The published Apple and Ryzen measurements must not be presented as Pixel measurements. [Model artifacts and desktop benchmarks](https://github.com/handy-computer/transcribe.cpp/blob/4807edaf210d0d7e8a6f7fb2a44b65966a2797f0/docs/models/parakeet-unified-en-0.6b.md).

## Android feasibility and gaps

An Android port is plausible, but upstream does not provide a finished Android integration. The binding list includes Python, TypeScript, Rust, and Swift; the inspected workflow definitions contain no Android target. A Kotlin app would need an NDK build and a small JNI wrapper for model load, stream feed/finalize, result copying, errors, and disposal. This is an inference from the C API and available build files, not a verified Android build. [Bindings list](https://github.com/handy-computer/transcribe.cpp/blob/4807edaf210d0d7e8a6f7fb2a44b65966a2797f0/README.md#bindings), [workflows](https://github.com/handy-computer/transcribe.cpp/tree/4807edaf210d0d7e8a6f7fb2a44b65966a2797f0/.github/workflows), [C API](https://github.com/handy-computer/transcribe.cpp/blob/4807edaf210d0d7e8a6f7fb2a44b65966a2797f0/include/transcribe.h).

Vendored ggml contains ARM quantization kernels, dot-product/int8 matrix feature checks, and an optional KleidiAI path that explicitly admits Android arm64. Its CPU implementation also contains Android-specific handling. This is stronger evidence than merely finding generic CMake files, but the integration still needs a cross-build and a real-device smoke test. Start with arm64; Outspoke currently also ships armeabi-v7a, which would need separate validation or an explicit model availability restriction. [CPU build definitions](https://github.com/handy-computer/transcribe.cpp/blob/4807edaf210d0d7e8a6f7fb2a44b65966a2797f0/ggml/src/ggml-cpu/CMakeLists.txt), [CPU Android handling](https://github.com/handy-computer/transcribe.cpp/blob/4807edaf210d0d7e8a6f7fb2a44b65966a2797f0/ggml/src/ggml-cpu/ggml-cpu.c), [Outspoke ABI splits](../app/build.gradle.kts).

Vulkan is an optional backend with host shader generation during cross-compilation. Device probing and CPU fallback exist in the public API. Whether the Pixel's driver supports the model's operations efficiently, and whether shader startup, memory use, or thermals offset its benefit, remains unmeasured. Treat Vulkan as a second experiment after CPU correctness. No Google Play Services dependency appears in the inspected native library/build path. [Vulkan build](https://github.com/handy-computer/transcribe.cpp/blob/4807edaf210d0d7e8a6f7fb2a44b65966a2797f0/ggml/src/ggml-vulkan/CMakeLists.txt), [backend selection API](https://github.com/handy-computer/transcribe.cpp/blob/4807edaf210d0d7e8a6f7fb2a44b65966a2797f0/include/transcribe.h#L683).

The C header explicitly allows ABI changes between pre-1.0 minor releases. Pin native source and JNI headers together. Compute must be serialized across all sessions of a loaded model, and result strings are borrowed until mutation, so copy strings before returning them to Kotlin. Outspoke's existing serialized repository sessions fit this constraint. Static transcribe/ggml libraries linked into one JNI library would avoid packaging dynamically discovered backend modules, but needs position-independent code and dependency auditing. [API lifetime and ABI contract](https://github.com/handy-computer/transcribe.cpp/blob/4807edaf210d0d7e8a6f7fb2a44b65966a2797f0/include/transcribe.h#L1), [build modes](https://github.com/handy-computer/transcribe.cpp/blob/4807edaf210d0d7e8a6f7fb2a44b65966a2797f0/CMakeLists.txt#L130).

## Decision path

First measure and tune the ONNX engine already on the phone. The investigation baseline used two intra-op threads, sequential execution, and BASIC graph optimization. The current implementation uses full graph optimization and up to four threads; the opt-in device benchmark compares 1/2/4. Benchmark thread counts and supported optimization levels on identical audio, with cold and warm results. Record encoder/decoder/frontend time, queued audio, and Stop-to-final time. Preserve transcript correctness when changing normalization or final-window geometry. [Current session configuration](../app/src/main/kotlin/outspoke/inference/ParakeetUnifiedEngine.kt).

If the encoder still misses the real-time budget, build a separate arm64 transcribe.cpp/JNI experiment behind the existing streaming engine interface. Compare the same clips, context geometry, warm model, and sustained recording duration against tuned ONNX. Check native memory, APK size, cancellation, model teardown, transcript accuracy, and thermal slowdown before choosing a runtime. A GGUF migration also needs new pinned model downloads and license attribution. Upstream library code is MIT; the Unified weights are CC-BY-4.0. [Library license](https://github.com/handy-computer/transcribe.cpp/blob/4807edaf210d0d7e8a6f7fb2a44b65966a2797f0/LICENSE), [weight provenance](https://github.com/handy-computer/transcribe.cpp/blob/4807edaf210d0d7e8a6f7fb2a44b65966a2797f0/docs/models/parakeet-unified-en-0.6b.md#download).

Previewing only in the keyboard and inserting once on successful Stop is independent of this runtime decision. It can match Handy's interaction sooner, while profiling identifies whether the remaining delay is queued compute, expensive final windows, or both.
